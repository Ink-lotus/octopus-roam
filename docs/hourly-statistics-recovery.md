# 遗留小时统计归档与恢复

本文描述v0.1.6源码继承的小时统计处理合同。[v0.1.4](releases/v0.1.4.md) 已发布的自动归档仅覆盖 SQLite；v0.1.5 将迁移 18 扩展到 MySQL/PostgreSQL。实际发布和两平台验收须绑定最终 commit 与产物，遵守 [release-ci.md](release-ci.md)；完成状态以对应发布记录为准。

旧程序把 `StatsHourly.Hour` 声明为可自增整数主键。保存午夜 `Hour=0` 的缓存快照时，ORM 可能省略主键，数据库生成递增编号。重复保存可能产生同一午夜统计的多份累计快照；落在合法小时内的错误值也无法只凭现库辨认。v0.1.3 的迁移 17 修正主键结构，但保留了已产生的越界行，随后严格缓存校验导致启动失败。

## 迁移 18

保留迁移 17，在 AutoMigrate 与迁移 16 后运行迁移 18。未升级的旧库和已完成 17 的失败启动库均进入相同处理流程。SQLite、MySQL、PostgreSQL 的自动隔离范围均为 `hour >= 24` 的持久化行；负数、错误总统计 ID、非法 API Key ID 等继续由原校验拒绝，不把所有非法输入都当作本次遗留故障。

迁移会把原小时、日期及全部七项指标写入 `stats_hourly_archives`。归档的 `payload` 逐列保留 SQLite 存储类型和值：整数使用十进制，REAL 使用 IEEE-754 位串，TEXT/BLOB 使用 Base64 原始字节，NULL 独立保留。不能把 NULL 当成零，不能将未知附加列忽略后声称归档完整。

归档 ID 为格式版本、来源、原小时和原始载荷的 SHA-256。逐行回读归档并核对全部字段，再次核对源行后才从活动小时表隔离。在同一个数据库事务内提交归档行、隔离操作和迁移 18 成功记录。原业务行没有归零、取模、移位或求和；合法小时、总统计、每日/API Key 统计与业务配置保持原值。归档不参与缓存、图表和任何统计累加。

归档表由 AutoMigrate 建立，故迁移 18 失败后可以留下空表及失败记录；数据事务中的部分归档、隔离和成功记录均须回滚。先前成功的迁移（含 17）继续保留，不能把整次跨版本升级描述成一个事务。修正具体失败条件后可重试启动；迁移状态和归档内容支持重复执行。

遇到相关自定义触发器、引用小时表/归档表的外键、未知列、存储类型不符、归档校验失败、读写失败或成功记录写入失败，迁移报告原因并中止。不要关闭外键约束、删除校验或手工将迁移标为成功。MySQL/PostgreSQL 的归档格式为 2，来源分别为 `mysql-migration-18` / `postgres-migration-18`，每列另存原生 SQL 类型。整数精确保留，NULL 不变成零，文本以 Base64 保留字节，32 位 FLOAT/REAL 和 64 位 DOUBLE 分别保留原始浮点位。MySQL 强制二进制预处理结果，PostgreSQL 使用原生发送函数，避免文本精度舍入；现有 SQLite 格式 1 与摘要保持兼容。

MySQL 要求源表、归档表、迁移记录表均为 InnoDB，事务隔离为 REPEATABLE READ 或 SERIALIZABLE；范围锁覆盖越界小时及归档。不会使用隐式提交的 LOCK TABLES 或在数据事务内执行 DDL。触发器元数据须完整可见；检查跨库外键的 INNODB_FOREIGN 需要 PROCESS 元数据访问权限。权限不足会明确报错并回滚，由管理员审阅权限或在受控维护连接执行，不自动扩大账号权限。PostgreSQL 在事务中锁定三表，检查触发器、规则、外键，并拒绝未审阅的 RLS、分区及继承。两者均在同一数据事务提交归档、回读核验、隔离及 18 成功记录；已记录 18 失败的实例可以重试。

## 加密备份与空库恢复

未使用扩展冷却时，仅含格式1归档的导出继续使用 `octopus-roam / 1004`，含任意格式2归档使用1005。任一规则使用Key作用域或开启 `notify_webhook` 时导出1006；1006允许两种小时归档共存。加密容器仍为1，新程序接受本产品1000～1006。格式2只能在1005/1006中使用，扩展冷却只能在1006中使用。`stats_hourly_archives`随完整加密备份导出；活动小时或归档损坏使导出失败，不生成声称成功的备份。

导入先验证版本、归档格式与摘要、唯一性及原有业务图。归档仅按内容 ID 插入，重复导入相同归档不新增、不覆盖；任何归档错误或写入失败会使整次导入回滚。归档与合法业务数据一起在空库恢复，重启后再次验证；已有本地归档不会阻塞合法的旧版本备份导入。导入后的归档不进入统计缓存。

1004/1005/1006备份须由支持相应内容版本及归档格式的程序恢复；1006须使用v0.1.6或后续兼容程序，v0.1.5及更早拒绝1006。三种数据库可恢复其他数据库的归档证据，不把归档重插入活动小时表。不能手改内容版本让旧程序忽略归档或扩展规则。保留原备份和升级前完整数据库副本，降级使用原程序配合该副本。

## 含异常小时的旧备份

普通导入仍拒绝 `stats_hourly` 中的越界或重复小时。对明确来源的本产品 1000～1003 加密备份，可使用显式离线命令 `backup-convert-hourly`，参数为 `--input`、`--output`、`--password-env` 以及确认归档语义的 `--archive-legacy-hours`。密码从调用者已准备好的专用环境变量读取，避免写进命令行和日志。

转换器不打开数据库，不覆盖输入或已有输出。它只把 `hour >= 24` 的旧备份记录转入 1004 的归档集合，保留合法小时与其他表数据；原小时和指标不作推断。重复/负数小时、非法日期或指标、引用不完整、上游无标识格式及其他版本仍拒绝。转换成功只输出归档数量及输入/输出 SHA-256。输出写入失败时输入保持不变，可能留下不完整的加密输出文件，应保留检查，不当成成功备份。

旧 JSON 只能保留其已有的类型和值，无法还原导出前 SQLite 的 NULL/存储类型；其来源标记为 `backup-1000`～`backup-1003`，与 `sqlite-migration-18` 区分。摘要只能检验内容一致性，不能证明文件来自可信实例。保留原始加密文件及转换报告，在隔离空库执行导入、再导出与重启验证后才考虑实际恢复。转换不会替代所有业务字段的普通导入验证。

## 审计与故障恢复

使用 [db-audit](backup-integrity.md) 的只读入口：新增归档表计数及内容摘要验证，输出不含载荷、凭据或连接信息。有效归档本身不是业务引用错误；审计说明其不参与活动统计。损坏归档使审计失败，启动与导出也会拒绝它。

迁移前后应在独立副本核验：合法小时逐行相等、归档与全部原越界行一一对应、活动越界数为零、其他统计与配置的摘要不变、SQLite quick_check 正常，以及加密备份在空实例的恢复与重导出一致。云端数量必须从该实例的独立证据得出，不能套用本地异常条数。

迁移失败保留原数据及失败证据，先定位磁盘/权限、表结构或归档核验问题。不要重复运行不清楚是否提交的远程操作。实际生产停止、备份、迁移、恢复和启动均须按当前会话的具体目标、命令与影响另行授权。
