# 升级、备份与故障排查

本文面向 [v0.1.6](releases/v0.1.6.md)，本版升级验收使用真实v0.1.5及升级前完整副本；保留真实v0.1.2、迁移17后启动失败的v0.1.3及更早版本首次布局迁移说明。v0.1.1 已整体移除隐私及凭据脱敏功能：设置页没有隐私开关、规则或预览入口；渠道和 Webhook 编辑先读取最新实际配置，未改字段按原值保存，显式修改或清空遵守原有业务校验，不识别历史掩码或猜测其原值。日志、按需诊断正文和通知在各自原有内容范围内使用原值，不新增请求 Header/Body 采集；历史日志中已替换的内容不能复原。

旧数据库中的 `privacy_protection_enabled` / `privacy_protection_rules` 行保持原样，启动与缓存忽略它们，不解析旧规则。含这两键的兼容旧备份可导入，新导出排除它们。旧 GET/POST `privacy-rules`、POST `privacy-preview` 和通用设置写入这两键，在管理员认证后返回 HTTP 410、`reason: feature_removed`；未认证仍返回 401。登录/API Key 鉴权与备份加密继续独立生效。

v0.1.1 的迁移 014/015 已提供冷却规则、平台分类及分组归属。v0.1.2 通过既有 AutoMigrate 为渠道增加 `strip_responses_history` 和 `custom_header_model_only`，旧数据均默认 false；已有规则、分类、凭据和选择保持。v0.1.4 新导出为 `octopus-roam` 内容 **1004**，加密容器仍为 **1**，新程序接受本产品 1000～1004。v0.1.5 保留 1004，并在包含 MySQL/PostgreSQL 格式 2 小时归档时使用 1005；新程序接受 1000～1005。v0.1.3 保持两个开关的已有值，但 Responses 历史清理收窄为只移除显式远端引用；其他历史、ID、密文及 include 原值保留，见[当前清理合同](responses-history-cleanup.md)。

v0.1.3 增加迁移 16/17：PostgreSQL 修复实体序列，三库修复小时、总统计、API Key 统计和迁移编号的错误自增结构；按 before → AutoMigrate → after 执行，真实 v0.1.2 升级先运行 before 17，再运行未完成的 after 16；v0.1.4 继续运行 after 18 的 SQLite 路径，v0.1.5 补齐 MySQL/PostgreSQL 路径。现有数据、索引和关联受到保护，不猜测移动旧错位统计。PostgreSQL 需要相应表/序列 ownership；不兼容自定义结构或权限不足时明确失败，保留现场后处理。备份导入使用[保守完整性合同](backup-integrity.md)，同 ID 的不兼容快照不再静默合并。

v0.1.4 保留迁移 17，新增迁移 18：对 SQLite 中 `hour >= 24` 的遗留行，先原样归档、回读核验，再在同一事务中从活动表隔离并记录成功。合法小时及其他统计和配置不变，不归零、取模或累加历史快照。归档进入 1004 备份和空库恢复；负数小时、损坏归档及其他非法输入继续拒绝。未升级旧库与已完成 17 的失败启动库均可升级。含越界行的旧加密备份须显式离线转换，原文件保持；详见[小时统计归档与恢复](hourly-statistics-recovery.md)。

v0.1.5 将迁移 18 扩展至 MySQL/PostgreSQL：对 `hour >= 24` 的遗留行原样归档，核验后在同一数据事务中从活动表隔离并记录成功。原始 SQL 类型、NULL、文本字节及浮点位保存在格式 2 归档中；包含格式 2 归档的导出使用 1005。MySQL 要求 InnoDB、REPEATABLE READ 或 SERIALIZABLE，以及完整触发器/外键元数据权限（外键检查需要 `PROCESS`）；PostgreSQL 要求可锁定相关表。未知列、触发器、外键、RLS、分区、继承或权限不足均会令迁移失败并保留数据。MySQL/PostgreSQL 仍属正式支持范围外。详细边界见[小时统计归档与恢复](hourly-statistics-recovery.md)。

正式支持 Windows amd64 原生 + SQLite 和 Linux amd64 Docker / Compose 镜像 + SQLite。C02 的首次开发产物应用验收已完成，v0.1.6 新候选仍须以自己的产物验收；准确输入见[支持矩阵](support.md)。WSL2 / WSL Containers 为预期兼容，不再单列必验项。已发布支持声明和历史 Windows/WSLc 记录保持原样。

## 升级与回滚

版本页只检查 Octopus Roam 自己的发布源，不会查询或下载上游项目。公开版本从本仓库 Release 获取；本地开发版显示“开发或本地构建”，不会提供更新按钮。独立镜像地址为 `ghcr.io/ink-lotus/octopus-roam`；部署本版时先确认 [v0.1.6 Release](https://github.com/Ink-lotus/octopus-roam/releases/tag/v0.1.6) 已公开，再使用准确的 `v0.1.6-amd64` 标签、显式选定 `linux/amd64` 的 `v0.1.6` 标签或已核对的 digest，并从同一 Release 下载程序与校验和。`latest` 只随正式稳定发布更新；以下步骤描述本版目标，不表示版本已经公开。

稳定版只接受更高稳定版；官方 RC 接受更高 RC 或对应的稳定版。版本比较按数字段和 RC 序号进行，不能按字符串排序。更新查询、归档和 `SHA256SUMS` 来自同一个独立版本；归档会先下载到隔离临时目录，校验 HTTP 状态、大小、路径和哈希后才替换程序。配置、数据库和备份目录不会从归档写入。Windows 更新在当前进程正常退出后由隐藏的本地辅助进程替换 exe，并保留更新前程序和菜单支持文件备份；Linux/macOS 在同一安装目录内完成原子替换后重启。容器内不替换程序文件，按镜像标签升级并重启容器。

如果独立发布源没有版本、当前已是最新、平台不支持在线替换或当前是本地构建，设置页分别显示对应状态。请求失败和校验失败会保留原程序；更新接口需要管理员认证，接口返回“已校验并准备重启”只表示替换流程已排队，不能据此证明新程序已经启动。确认完成时，应重新登录并核对运行版本与本次接受的目标完全一致。成功必须以本次运行版本和更新后数据核对结果为准。

v0.1.1 已验证旧 v0.1.0 的首次升级和原生助手更新/失败恢复。既有版本验收不替代自己部署的升级检查；使用准确目标产物按以下步骤核对数据与运行状态。后续发布的 Windows / Linux 容器验收遵守[发布门禁](release-ci.md)，运行目录安排见[本地部署说明](local-deployment.md)。

1. 记录当前构建和配置，正常停止旧服务，让内存统计落盘。使用数据库原生工具或停机副本保留升级前数据库；SQLite 应保留完整数据目录，包括尚未检查点合并的 WAL 文件，勿只复制一个运行中的 `.db`。
2. 在隔离目录/数据库副本上启动新构建。核对编号迁移、AutoMigrate、渠道、Key 启停、模型授权、分类归属、分组模式/当前成员、路由参数和统计；从 v0.1.2 升级核对迁移 16/17、已有兼容开关值、保守导入和小时统计；从 v0.1.1 升级时两个兼容开关默认关闭。从 v0.1.0 升级时还应验证空冷却规则与未分类默认值。再次正常停止、重启后检查持久化。
3. 在设置页输入至少 12 个字符的备份口令，重复确认后导出 `.encrypted.json`。在另一个隔离实例中导入，确认可恢复后再切换业务实例。
4. 回滚时停止新服务，使用**升级前的构建、配置和完整数据库快照**。不承诺旧程序直接读取新数据库；1004 备份须由 v0.1.4 或后续兼容程序恢复，1005 备份须由 v0.1.5 或后续兼容程序恢复，1006须由v0.1.6或后续兼容程序恢复；v0.1.5及更早拒绝1006，不能手改版本号降级。增量 JSON 导入也不会删除现有多余记录，不能充当整库回滚。恢复升级前快照会丢失升级后的新增数据。

升级验收需覆盖规则、分类和两个渠道开关共同恢复、遗留隐私设置退役、失败无部分写入，以及真实旧程序拒绝 1004/1005 且数据不变、迁移 18 原样归档及重复启动、归档随备份空库恢复。数据库迁移记录保留，不能通过删除记录或手改版本号冒充完成迁移。MySQL/PostgreSQL 的已有功能和测试继续保留，未扩大正式支持范围。

## 从 v0.1.2 / v0.1.1 / v0.1.0 升级与容器升级

v0.1.1 Windows 程序采用原生菜单控制和更新助手；v0.1.0 仍使用旧版 PowerShell 布局。首次从旧版 PowerShell 布局切换到仅含 cmd 入口的新布局需要手动升级，旧版在线更新器不能识别新包；请按[本地迁移步骤](local-deployment.md#从旧脚本布局迁移)同时替换 exe 和 cmd，并处理属于该部署的旧登录快捷方式。

完成首次手动迁移后，新版 Windows amd64 非容器实例可使用原生更新助手。后续更新前重新查询版本，确认准确目标；遇到 409 时刷新版本信息后重新确认。接口回执中的目标和重启后的运行版本必须一致，刷新页面后还需确认前端版本。从 v0.1.2 / v0.1.1 升级可沿用该原生助手，成功后仍需核对实际版本和数据。

稳定版本只选择更高稳定版本，不接受 RC；RC 可升级到更高 RC 或更高稳定版本。版本来源为[本仓库 Releases](https://github.com/Ink-lotus/octopus-roam/releases)，以版本页实际公开的稳定版及摘要为准，先核对本次 v0.1.6 目标是否可用，不应转而下载上游或把 RC 当作稳定版。

### Linux amd64 / Docker Engine

容器内的版本页提示按镜像升级。下面是 Linux 容器的升级与恢复步骤；C02 首次开发验收已有证据，本次新候选仍须逐项执行并留证：

1. 记录旧容器的准确镜像标签/digest、数据目录、端口和环境变量；能够正常启动时导出加密备份。若已因小时越界无法启动，保留失败日志，先停止容器并保存下一步的完整数据副本，不为导出强行跳过校验。
2. 用 `docker stop -t 30 <旧容器名>` 正常停止，并确认容器已退出；将完整宿主数据目录复制到新的备份目录，保留文件所有权和权限并核对副本。保留停止的原容器和旧镜像，不能只复制运行中的 SQLite `.db`。
3. 核对目标版本的发布材料，拉取并核对准确镜像身份，例如 `docker pull ghcr.io/ink-lotus/octopus-roam:v0.1.6-amd64`。创建新名称的容器，保留原挂载、端口、`PUID` / `PGID` 和必要环境变量；启动结构见 [README](../README_zh.md)，使用本次目标标签或 digest。
4. 数据目录位于 Linux 文件系统并挂载到 `/app/data`；核对实际应用用户的读写权限。同一数据目录一次只交给一个应用实例，先在隔离副本上演练升级。登录核对运行版本、设置、渠道、禁用状态和分组，正常停止 / 重启后再次核对。
5. 正常停止后，再以同一数据卷和准确镜像创建另一名称的容器，核对容器重建后的数据一致性；另用空数据目录验证当前加密备份恢复。
6. 新部署失败时先正常停止它，将升级前完整数据副本复制到新的恢复目录，并以旧镜像和该恢复目录新建容器。保留失败现场；仅将旧镜像连接已迁移目录不能作为可靠恢复。

### Docker Compose

Compose 与上面的 Linux 容器使用同一支持目标和验收要求。升级前记录旧镜像标签/digest 与实际生效的 Compose 配置；用 `docker compose stop -t 30 octopus-roam` 正常停止后保存完整数据副本，并保留原挂载、环境变量、运行用户和端口设置。完成这些步骤后，在 `docker-compose.yml` 所在目录的 Linux shell 中设置准确目标标签：

```bash
export OCTOPUS_ROAM_VERSION='v0.1.6-amd64'
docker compose config --quiet
docker compose pull octopus-roam
docker compose up -d octopus-roam
```

Compose 更新会替换该服务的旧容器，升级前须已保存旧镜像身份、配置和完整数据副本。核对新容器实际镜像 digest、页面运行版本和原有设置 / 渠道 / 分组，再验证正常重启及同卷重建后的持久化。正式版本更新 `latest`，RC 不更新稳定标签。如果升级失败，先正常停止本次容器，按升级前镜像与升级前完整数据副本恢复，保留失败日志和原镜像，不删除数据卷。仅把旧镜像连接已被新版本迁移的数据目录不构成可靠回滚。

### WSL2 / WSL Containers 及其他环境

WSL2 / WSL Containers 为预期兼容环境，不再要求指定 WSLc 版本或单独的发布验收。已有 WSLc 部署可用其管理工具执行同样的记录镜像、备份、正常停止、换镜像和恢复流程；Windows 挂载、文件权限及网络差异按实际环境核对。Linux 容器验收不代表这些宿主集成行为全部等价。

Linux 原生、macOS、Android 和其他架构镜像继续作为实验性构建。MySQL/PostgreSQL、外部数据库、其他容器运行时和反向代理等组合保持正式支持范围外状态；当前矩阵与 Linux 开发/候选验收边界见[支持范围](support.md)。

## 加密备份

下载文件使用 scrypt 派生密钥和 AES-256-GCM 加密完整备份，包含可恢复的渠道 Key、客户端 API Key、Webhook 认证头及配置。口令不保存在服务器，也不能找回；它独立于登录密码。请单独保管口令，使用 HTTPS 传输。备份加密不改变业务数据库本身的存储方式。

备份包含渠道（含冷却规则和两个兼容开关）、凭据、模型、授权、平台分类、分组归属、成员、模型价格、API Key、设置、Webhook、活动统计与遗留小时归档。管理登录账号、迁移记录、内存路由/冷却状态、缓存/SSE 版本、日志和刷新诊断不在 JSON 备份中；完整灾备仍需数据库和配置副本。

| 文件 | 导入行为 |
| --- | --- |
| 本产品加密容器 `version: 1`，内层 `octopus-roam` / `1000`～`1006` | 提供正确口令并通过内容校验后导入；1004/1005/1006 的恢复版本要求见下文 |
| 本产品明文 `product: "octopus-roam"` / `version: 1000`～`1006` | v0.1.6 可导入；正常 UI 导出只产生加密文件 |
| 无产品标识的上游 `0` / `5` | 保留裸 JSON、API 响应包裹及 multipart 导入 |
| 无标识 `6`（阶段 4/5 预发布格式） | 明确拒绝；用新构建打开原数据库后重新导出 |
| 外来标识、未知容器/内容版本、混合响应包裹 | 拒绝 |

只有旧 `6` 号 JSON、没有原数据库的情况下，本版本不提供直接恢复路径。不要手改版本号绕过身份检查。

导入采用保守增量语义：同 ID 实体的配置、凭据和父归属必须兼容，不同 ID 命中同一业务唯一键时拒绝；输入必须自含完整引用。冲突返回 409，整次拒绝，不静默覆盖或换接。兼容快照按[逐表合同](backup-integrity.md)导入统计并保留约定的本地状态；新增禁用状态保持，兼容的已有渠道 Key 按备份覆盖启停状态。写入与提交前检查在同一事务中完成。

已有渠道的规则和兼容开关也参与配置兼容校验；合法重放按合同保留本地启用、跟随刷新、并发限制等状态，已有分组保留本地分类与当前成员。分类继续按去除首尾空白、转小写后的名称归并，保留本地显示名称，先预留可用输入 ID，再分配冲突 ID 并映射分类引用。空库恢复才能完整还原合法备份配置，增量导入不能当作强制覆盖恢复。

内容 1001 起支持规则和分类，1002 起支持 `strip_responses_history`，1003 起支持 `custom_header_model_only`。缺失的新开关默认 false；旧版本声明夹带尚不支持的启用状态时拒绝。显式 null 的规则/分类数组、非法规则、重复/非法分类或悬空归属均拒绝，失败不产生部分写入。旧 1000 或上游 0/5 缺新字段时使用空规则/未分类；遗留隐私键只作退役过滤。内容 1004 起包含独立的 `stats_hourly_archives`；含格式 2 原生类型归档时使用 1005。两种格式均只接受校验通过的归档；不支持向 v0.1.3 或更旧程序降级恢复。

内层 JSON 上限 64 MiB，上传请求上限 96 MiB，单进程同时处理一个备份任务。超大实例使用原生数据库备份。错误口令或内容篡改返回同一错误；不会把解密失败的文件转当明文导入。

## v0.1.6 冷却、模型过滤与旧模板

全局与渠道共享可视化模型过滤弹窗；手写表达式无法还原时可清空进入可视化草稿，取消保留原值。外部表达式预览按内容自然增高、最大144px并内部滚动。后端保留原正则字段，F06实际模型列表预览和样例测试未包含在本版。

Key作用域覆盖同一渠道中该Key的全部模型，其他Key不受该规则影响。旧规则缺少 `notify_webhook` 时默认关闭；新冷却期通知，活动期间延长不重复通知。使用Key作用域或任一规则开启通知时导出1006，可以同时包含格式1/2小时归档。没有扩展冷却时仍按既有规则导出1004/1005；加密容器仍为1。1006与各内容版本的完整性和冲突保护继续生效。

旧Webhook模板继续按原 `failure` 样例校验，可创建、编辑、禁用和恢复；真实发送前仍检查最终JSON。旧自定义模板要接收 `cooldown` 通知，须添加有效的对应分支；默认新模板已经支持。升级、空库恢复和重复导入均须核对这些字段及旧模板，真实v0.1.5拒绝1006时应确认数据不变。

## 脚本接口变化

- 导出改为已认证的 `POST /api/v1/setting/export`，JSON 请求体 `{ "password": "<备份口令>" }`，响应为加密 JSON 下载。旧 `GET` 返回 `405`。
- 导入仍为已认证的 `POST /api/v1/setting/import`，multipart 字段 `file` 和 `password`；旧明文文件不需要口令，原有裸 JSON 上传继续支持。
- 口令不要放入 URL、日志、共享脚本或持久配置。导出/导入忙碌返回 `429`，超限返回 `413`，无效文件或口令返回 `400`。身份或引用冲突返回 `409` 且未导入；数据库事务/写入失败返回通用 `500` 并回滚。若已提交但完整缓存发布失败，返回 `503` 并暂停相关操作，应保留数据库后重启服务，不重复导入。

## 配置默认值与操作规则

运行配置仍使用 `data/config.json` 或 `--config` 指定文件；环境变量前缀仍是 `OCTOPUS_ROAM_`。新增产品设置保存于数据库，不能当成 config.json 字段。

| 配置 | 默认值 / 行为 |
| --- | --- |
| `channel_auto_update_enabled` | `false`，全局自动更新默认关闭 |
| `channel_auto_update_interval_minutes` | `1440`，可设置 1–10080 分钟 |
| `channel_auto_update_auto_add_groups` | `false`，不自动追加分组成员 |
| 渠道 `follow_global_auto_update` | 旧值缺省按 `true`；显式 `false` 保留；退出后不参与自动更新和批量刷新 |
| 渠道 `strip_responses_history` | `false`；开启后只移除最终 Responses 的顶层 previous_response_id 和 input 第一层 item_reference |
| 渠道 `custom_header_model_only` | `false`；开启后自定义 Header 仅用于模型获取与刷新 |
| `codex_catalog.enabled` / `codex_catalog.use_proxy` | 分别默认为 `true` / `false`；配置/环境变量控制，重启生效，见[接入说明](codex-catalog.md) |
| 渠道 `max_concurrency` | `0` 不限；正数为跨 Key、跨分组共用额度 |
| 渠道 `allowed_protocols` | 缺省或 `0` 兼容全部现有协议（有效掩码 `14`） |
| 渠道 `cooldown_rules` | 默认 `[]`，只在高级设置中手动添加；错误码/关键词双填为 AND，秒数 `1..2147483647`，模型级/渠道级跨分组共享 |
| 分组 `category_id` | 默认 null（未分类）；一层手动分类，删除分类仅解除归属 |
| 分组 `model_match_mode` | `keyword`；`exact` 完整匹配，均忽略大小写并按规则去首尾空格 |
| `webhook_manual_failure_threshold` | `10` |
| `webhook_failover_channel_threshold` | `3` |

全局 `group_route_defaults` 只设置路由策略。未勾选覆盖时只影响新分组；覆盖时保留已有分组的 `manual`/`failover` 模式、成员顺序与手动当前成员。新安装默认使用指数退避：初始 1 秒、每次翻倍，最大间隔默认 600 秒，可按需设为更长时间；选择固定模式时默认间隔为 3 秒。已有全局策略及分组的显式配置继续生效，旧配置缺少重试模式时仍按固定间隔处理。手动总尝试次数 `0` 表示不限；故障转移每成员 2 次、冷却 60 秒；非流式完整响应超时 120 秒、流式首事件超时 30 秒。旧 affinity 字段有效值为 `0`。

模型刷新所有 Key 成功后才提交；任一失败保留旧模型、授权和分组成员。成功返回空列表会清空模型及失效成员，但渠道和分组实体仍在。自动追加只作用于已有分组，严格匹配不会把带后缀的模型加进同名前缀分组。启用自动更新前应确认供应商模型列表可靠，成功空结果会影响后续路由。

两页批量刷新共享同一个任务，只选择启用渠道，实际探测前再次复核，禁用/删除/正在刷新者正常跳过。搜索与分类筛选不缩小任务范围；切页继续执行，重复点击不重入。显式单渠道刷新兼容，已发出的请求无法撤回。

冷却规则只匹配实际 Relay 上游失败，关键词检查有界错误消息；正常输出、prompt、客户端取消和模型列表探测不触发。模型级按该渠道的实际上游模型跨 Key/授权/分组共享，渠道级覆盖整个渠道；多来源取较晚截止。等待释放并发额度，原成员解除操作不清除共享规则。配置持久化，运行倒计时仅在进程内、重启清空；规则或出站连接/凭据变化使旧状态失效，展示名称、分类、成功或模型刷新不提前解除。

分类和归属保存在服务端；分类筛选与折叠为浏览器偏好。分类变化只影响展示，保持路由、失败计数、成员顺序、手动选择及冷却状态。

## 日志与排障

请求状态：`running` 表示选路、排队或请求中；`committed` 表示首字节已交付，此后不能重试；`success` 为完整交付；`failed` 为失败结束；`canceled` 为客户端取消。渠道状态另分 `waiting`、`normal`、`error`。请求中日志置顶，筛选影响展示，不更改执行状态；SSE 断线后重新连接并刷新状态。

| 现象 | 检查与处理 |
| --- | --- |
| 刷新时 Key 失败 | 展开渠道刷新详情，检查该 Key、供应商地址和协议路径；旧模型保留。不要通过重复提交覆盖正在运行的刷新。 |
| 模型变为空 | 区分成功空结果与请求失败；检查全局/渠道正则过滤和供应商权限。补齐模型授权后重新同步已有分组。 |
| 请求并发排队 | 查看渠道占用/等待数；流式请求直到结束才释放额度。检查长流或取消情况，再按供应商额度调整上限。 |
| 规则冷却仍未结束 | 查看命中规则、实际模型/渠道范围及剩余时间；多个来源取较晚截止。成功、模型刷新及“解除成员冷却”不清除共享规则状态。 |
| Webhook 失败 | 使用测试发送检查 URL、认证头、超时与目标端状态；v0.1.1 的通知错误保留原值，发送失败仍只报告原有固定分类和状态码。失败阈值通知与恢复通知各自去重。 |
| 备份口令错误或文件损坏 | 核对该文件的口令，含首尾空格；使用未修改的原文件。不能通过改变格式字段恢复。 |
| 兼容重放后本地状态未变化 | 启用、并发、分类等按逐表合同保留；完整恢复使用空实例或完整副本。 |
| 导入返回 409 | 核对表、ID、配置和引用冲突；不重复拼接不同快照。 |
| 导入返回 503 | 数据库已提交但缓存未发布；保留数据并重启，不重复导入。 |
| 隐藏的禁用渠道找不到 | 在渠道筛选中切到“全部”或“禁用”；筛选不删除渠道，也不改变备份内容。 |

加密容器机制见[加密设计](backup-encryption-design.md)；本版内容字段和迁移边界以本页及 [v0.1.6 说明](releases/v0.1.6.md)为准。个别渠道的 Anthropic 模型探测告警见 [BUG-001](known-bugs.md)，本版不增加该鉴权回退。
