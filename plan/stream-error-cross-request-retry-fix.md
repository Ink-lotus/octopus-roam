## 3. 问题与已确认的代码证据

用户观察到类似错误：

```text
error: responses stream error, type: stream_error
```

连续出现时，界面可能显示多个新请求，每个请求的错误次数很低，成员的重试等待和告警阈值没有累计。

### 3.1 当前链路

```text
客户端请求 A
  → 新建 RequestState，初始化请求内尝试次数和错误数
  → 收到 response.created 或 response.in_progress
  → 首事件通过检查，调用 recordRouteSuccess
  → 写入并 Flush 到客户端
  → 后续收到 error / response.failed 等错误
  → 记录本请求失败并 return，未进入前面的重试与路由失败分支

如果客户端随后重发：
客户端请求 B
  → 新建 RequestState，计数从零开始
  → 再次使用原成员，重复上述过程
```

转发函数在提交后错误分支会直接返回。当前证据支持“请求结束后，客户端或前置组件重发可能形成循环”，没有证据证明服务端在该分支主动创建了新的入站 HTTP 请求。

### 3.2 代码定位

行号会变化，实施时以文件和函数名定位。

| 位置 | 已确认的行为 | 对本问题的影响 |
| --- | --- | --- |
| [upstream.go](../internal/relay/upstream.go) 的 `sendPassthroughStream`、`sendConverted` | 遇到首个非空、`inspectStreamEvent` 未报错的事件即返回 | 元数据事件也可能进入提交阶段 |
| [protocol.go](../internal/relay/protocol.go) 的 `inspectStreamEvent` | Responses 的 `type: error` 被识别为 `stream_error`；缺少顶层 message 时使用 `responses stream error` | 错误类型已经能够被识别；文案是回退值，不能仅凭文案认定所有真实原因相同 |
| [handler.go](../internal/relay/handler.go) 的 `Forward` | 首事件取得后调用 `recordRouteSuccess`，随后开始写流 | 恢复探测可能在流完整结束前被标为成功 |
| 同文件的发送错误分支 | 调用 `finishRound`、累计请求内 `failures`、计算 `RetryDelay`、调用 `recordRouteFailure` | 提交前失败能够使用当前重试流程 |
| 同文件的流结束分支 | 更新渠道统计和请求终态；提交后流错误直接结束请求 | 提交后的上游失败没有进入路由失败累计和共享退避 |
| [route.go](../internal/relay/route.go) 的 `routeRuntime`、`recordRouteFailureAt` | 冷却跨请求共享，但传入的 `failures` 来自单个请求；手动模式直接跳过路由失败处理 | 已有冷却可以复用，故障次数和手动模式保护需要补齐 |
| [state.go](../internal/relay/state.go) 的 `RequestState`、`newRequestState` | `ErrorCount`、`Attempt`、`RetryCount` 都属于一个客户端请求 | 新 HTTP 请求不会继承这些计数 |
| 同文件的 `markFailed` | 根据最终错误文案是否等于 `LastError` 判断是否加一 | 不同尝试发生相同错误时存在漏计隐患，应按尝试身份去重 |
| [runtime.go](../internal/relay/runtime.go) 的 `runtimeSnapshotLocked` | 按分组选一条请求，活跃优先、同类取最新，复制其遥测值 | 当前 `GroupRuntime.ErrorCount` 也不是跨请求故障总数 |
| [service.go](../internal/webhook/service.go) 的 `observeRequest`、`reopenRequestStream` | 手动通知依赖单条请求的 `ErrorCount` 达到阈值 | 多次请求各失败一次，可能始终不告警 |

### 3.3 与成功判定相关的缺口

`Forward` 在首事件之后调用 `result.events.Next()`，如果迭代结束且 `Err()` 为 nil，即使没有收到协议成功终态，也可能走到成功分支。`AggregateStreamChunks` 的错误目前主要影响用量提取，没有统一决定请求成败。

第一阶段需要覆盖“没有成功终态的 EOF 不能清除共享故障”的规则。各协议和转换库是否会消费终态、如何暴露完整结束，需要实现者读取实际依赖代码并用测试确认。不能简单要求所有协议都出现同一种结束标记，也不能把单纯的用量聚合失败一律算作上游故障。

## 4. 阶段范围与验收目标

### 4.1 第一阶段：必须形成完整闭环

1. 为分组成员维护跨 HTTP 请求的故障状态。
2. 提交前失败和提交后上游流失败进入统一的尝试结果结算，分别更新请求遥测与共享状态。
3. 手动模式和故障转移模式的新请求都检查共享退避；冷却后限制恢复探测数量。
4. 完整、合法的上游成功结果才能确认恢复；首帧和冷却到期不能独立确认恢复。
5. 手动告警使用共享故障次数，故障转移告警接收提交后错误造成的路由变化。
6. 相同错误发生在不同尝试时分别计数，同一次尝试只计一次。
7. 添加实际覆盖上述行为的测试，并完成对应检查。

第一阶段完成后，“前导事件 → 错误”仍可能结束当前请求；下一次请求必须受到共享故障保护。第一阶段不以消除客户端的新请求为验收条件。

### 4.2 第二阶段：另行实施

第二阶段暂存明确的前导事件，在真正输出或合法成功终态到达后再提交，使更多早期错误能留在原请求内重试。详细边界见第 13 节。

### 4.3 第一阶段规模边界

主要改动集中在 Relay 请求处理、路由及共享健康状态、计数和 Webhook 消费逻辑，以及相应测试。共享状态可新增一个局部源文件承载，避免继续增加 `handler.go` 的条件分支。

独立的前端仪表盘、新的可配置阈值体系、客户端请求内容去重、跨进程分布式限流、渠道协议库升级均不属于第一阶段目标。

## 5. 计数、作用域与配置约定

### 5.1 请求计数与成员故障状态

| 数据 | 作用域 | 更新和清零规则 |
| --- | --- | --- |
| `RequestState.Attempt`、`RetryCount` | 一个客户端请求中的当前成员尝试 | 保留现有成员切换和有效路由恢复代数的语义；新请求从零开始；等待不算尝试 |
| `RequestState.ErrorCount` | 一个客户端请求 | 每次不同的渠道或上游失败加一；请求内成功不能抹去历史错误 |
| 建议新增的 `FailureStreak` | 同一配置身份下的分组成员，跨请求 | 不同上游尝试失败分别增加；确认恢复后清零 |
| 建议新增的 `RetryNotBefore` | 同一分组成员，跨请求 | 给出下一次允许发起上游请求的绝对时间；新请求不能跳过 |
| 故障期标识和版本 | 同一成员的当前故障过程 | 用于恢复资格、告警去重和拒绝过期结果 |

建议共享键使用 `GroupID + GroupItem.ID`，并绑定该成员的有效配置身份。身份使用内部 ID 和版本，不能使用 API Key 明文、请求正文或错误文本。

采用分组成员作用域，可沿用各分组不同的重试配置、模式和模型授权关系。第一阶段不将某个分组的一次模型错误扩大成整个渠道所有模型、凭据和分组的停用。

不通过请求内容相同来判断是否是“同一次业务请求”。合法的新请求也可能内容相同，共享保护直接作用于成员即可。

### 5.2 复用现有配置的建议规则

| 现有配置 | 第一阶段建议用途 |
| --- | --- |
| `retry_mode`、固定或指数间隔配置 | 用共享 `FailureStreak` 计算该成员的下一次允许时间，复用 `RetryDelay` 的边界处理 |
| `member_max_attempts` | 保留现有请求内尝试上限；同时作为该成员跨请求连续失败触发故障转移冷却的阈值 |
| `member_cooldown_seconds` | 故障转移成员达到阈值后的冷却时间 |
| `manual_max_attempts` | 仍限制单个请求实际发送的尝试数；不能用共享失败数直接判定一个新请求已经耗尽预算 |
| 手动 Webhook 失败阈值 | 改为比较当前成员的共享 `FailureStreak` |
| 故障转移 Webhook 失效成员阈值 | 保留按冷却成员数触发的现有含义，并补齐恢复确认条件 |

其中，“`member_max_attempts` 同时触发跨请求冷却”是本方案建议新增的行为，实施说明和测试必须明确记录。多个并发请求共同失败时，一个请求可能尚未耗尽自身尝试上限，成员就已被共享保护置入冷却。这与“成员已经由其他请求确认不可用，后续选路必须遵守冷却”的行为一致。

`manual_max_attempts = 0` 保留不限次数的现有配置含义。持续故障时仍允许按间隔等待恢复，但必须满足服务端退避和告警要求。本文没有新增强制的业务总超时或把客户端重试次数强制设为有限。

固定间隔继续按固定间隔执行，指数模式才逐次增加。不能为修复本问题悄悄把所有分组改为指数重试。

## 6. 共享状态与并发规则

### 6.1 建议状态内容

具体类型名由实现者决定，至少需要表达：

- 成员和有效配置身份。
- 共享连续失败次数、最后一次脱敏错误、最后失败时间。
- 共享退避截止时间，必要时引用已有路由冷却时间。
- 当前是否处于故障期，以及故障期标识。
- 当前恢复探测持有者，以及能验证结果是否仍有效的版本。
- 订阅通知或等待唤醒所需的版本、通道。

共享数据必须由明确的互斥机制保护。不要把新的可变 map 指针直接放进当前按值复制的 `RequestState` 快照。

建议优先扩展既有路由运行态，或与路由采用清晰的同锁操作；如果单独设锁，必须明确锁顺序。当前请求状态使用 `mu`，路由使用 `routeMu`，渠道并发额度还有独立锁。不能在这些锁之间增加相反方向的嵌套调用。

### 6.2 状态转移

| 当前状态 | 事件 | 下一步 |
| --- | --- | --- |
| 健康 | 上游尝试失败 | 打开故障期、增加共享计数、设置退避；符合故障转移阈值时进入冷却 |
| 退避或冷却 | 新请求到来 | 等待允许时间，或在故障转移模式选择可用的其他成员 |
| 退避或冷却到期 | 有请求竞争恢复资格 | 原子地放行一个恢复探测；其他请求继续等待或选择其他可用成员 |
| 探测中 | 只收到首帧 | 继续持有恢复资格，尚未确认健康 |
| 探测中 | 有效的完整成功结果 | 结束故障期、清零连续失败、清除对应等待、唤醒等待者 |
| 探测中 | 上游失败 | 增加连续失败并设置新的退避或冷却，再释放探测资格 |
| 探测中 | 客户端取消、人工中止或尚未发送就放弃 | 归还资格，不清零已有故障，不增加上游失败 |
| 任意状态 | 有效配置身份被替换或成员删除 | 使旧结果失效，清理或迁移对应状态，并唤醒等待者重新选路 |

健康时不因这个修复把所有正常请求改成串行。故障发生前已经在途的请求可以完成；故障确认后，新取得发送资格的请求才受共享保护。并发测试应允许故障确认前已有的有限在途请求。

故障转移模式应保留现有分组恢复探测的互斥约束；手动模式也需要成员级恢复资格，不能因现有 `ProbeItemID` 只服务故障转移而漏掉手动模式。

### 6.3 旧请求和恢复资格

必须覆盖以下顺序：

1. A、B 在成员健康时同时发出。
2. A 失败，成员进入退避。
3. B 随后完成成功。
4. B 不具有本次故障后的恢复探测资格，不能清空 A 造成的退避。
5. 退避结束后取得资格的 C 完整成功，才允许恢复。

在同一有效配置和同一尚未恢复的故障过程中，其他已在途请求的真实失败应分别计数。有效恢复完成后，旧故障过程的迟到失败不能重新打开已结束的故障；它仍可写入原请求的历史失败记录。

实现可使用配置身份、故障过程版本和尝试令牌组合表达这些条件。路由当前使用的 `Generation` 会在选路和探测变化时递增，不能直接把它当成所有共享健康记录的唯一生命周期：普通的故障转移或退避通知不能把尚未恢复成员的连续失败数清零。

新共享状态发出的等待通知也不能让 `Forward` 误以为成员已经更换，从而不断重置 `Attempt` 或手动预算。区分“状态需要重读”和“实际预算身份变化”。

### 6.4 生命周期

- 新请求创建、旧请求结束、日志裁剪至 50 条、日志清空：不能清除共享故障。
- 普通退避、冷却到期、探测开始、选到其他成员：不能当作原成员恢复。
- 明确的成员或配置替换：使旧身份失效；沿用现有路由配置重置机制，并检查相关入口。
- 纯通知、并发额度变化：不能不加区分地抹掉故障。
- 分组删除、整体配置导入和运行态重置：回收对应状态及等待者，防止旧结果重建已删除成员。
- 进程重启：第一阶段的内存故障状态会清空。跨进程和跨重启保留属于后续能力。

需要检查 `ResetRouteState`、`ResetRouteStateForGroup`、`NotifyRouteStateChanged`、`ResetAllRouteStates`、渠道刷新回调，以及相关 handler 的调用关系。

## 7. 尝试结果统一结算

### 7.1 一次尝试只结算一次

建议为每轮实际尝试建立明确身份，例如请求 ID 与 Round 的组合或独立尝试令牌，并记录是否已经结算。

`finishRound`、流结束处理、`markFailed` 可能都接触同一个失败。它们应共享“一次尝试已结算”的事实，避免同一次失败加两次；不同尝试即使错误字符串完全相同也必须分别加一。

请求未真正发出时继续沿用 `sent` 的语义，不因增加共享保护而消耗请求尝试预算。授权缺失、渠道删除和出站构造错误可以保留现有错误展示、固定等待及故障转移配置错误处理，但不能伪造一次已经发送的上游尝试。

### 7.2 归因与处理表

| 结果 | 请求处理 | 共享成员健康处理 |
| --- | --- | --- |
| 发送后的上游 HTTP 错误、连接错误、上游响应超时 | 提交前按现有重试策略继续或结束 | 记录一次真实失败并施加共享保护 |
| 首事件即协议错误 | 提交前处理，保留原请求重试机会 | 同上 |
| 已提交后收到 `stream_error`、`response.failed` 等已识别上游失败 | 脱敏后按现有协议转发错误并结束当前流 | 记录失败、更新共享退避或冷却 |
| 上游流读取错误，或按协议确认的异常 EOF | 请求失败；提交后不重放 | 记录失败 |
| 完整、合法的非流式上游响应 | 正常完成上游结算，客户端写出另行处理 | 按有效版本及恢复资格确认成功 |
| 流式协议明确成功终态 | 结束读取并正常结算 | 按有效版本及恢复资格确认成功 |
| 客户端取消或人工中止 | 请求记为取消或中止 | 不增加故障，也不能清除旧故障；归还恢复资格 |
| 客户端写入失败、断开连接 | 请求交付失败或取消 | 不直接归因为上游失败；若上游完整成功已独立确认，可保留其成功结论，否则保持未知 |
| 渠道容量不足、等待时配置改变 | 等待或重新选路 | 不增加上游故障、不消耗尝试次数 |
| 入站 JSON、模型权限等请求校验错误 | 按现有请求错误返回 | 不进入成员故障统计 |

第一阶段不根据 `responses stream error` 这段文案写专用规则，应该消费已有结构化错误和真实的发送、取消、终态信息。对于当前已有 `response.incomplete` 等协议分类，优先保持兼容；若要区分长度限制等原因，需补充对应测试和变更说明，不能顺便重写全部错误分类。

### 7.3 成功时机与资源释放

`finishRound("", false)` 当前表达取得可提交响应，可以继续用于请求进度；共享健康状态的成功结算应移到上游完整成功的位置。流式首帧后继续保存必要的成员身份、版本和探测令牌。

不能只把 `recordRouteSuccess` 移到函数结尾就认为修复完成，还需要覆盖流错误、取消、未发送、资源释放和版本检查。

每个退出路径均须正确释放上游事件流、独占连接池、渠道并发额度以及恢复探测资格。确认共享失败并设置截止时间后，再唤醒新的竞争者；避免先放开资格、后设置退避产生发送窗口。

如果依赖已经消费某协议的结束事件，应通过可靠的完成信息判断成功。仅有 `Err() == nil`、收到任意首帧或成功聚合出部分文本，都不足以证明整个上游响应成功。

## 8. 发送前保护与退避计算

### 8.1 推荐流程

```text
读取配置并选择成员
  → 检查共享退避、冷却及恢复占用
  → 需要等待则发布现有等待遥测，等待截止时间或状态通知
  → 有机会发送时取得渠道容量
  → 在发送前重新检查配置与共享健康，并原子取得必要的恢复资格
  → 条件已变化则释放容量和资格，重新选路或等待
  → 真正发送上游请求
  → 对上游结果执行一次结算
```

现有 `pickGroupItem` 可能已经取得路由恢复令牌，整合时应复用它，避免建立两个互不协调的探测所有者。现有 `tryAcquireChannelCapacity` 的“恢复探测不持有选路权排队”规则也需要保留。

发送前的检查必须足够靠近实际发送。仅在请求刚进入 handler 时检查一次，会让早已排队的请求绕过随后发生的故障。

不要在等待共享退避时长期持有渠道容量。健康状态锁也不能覆盖网络调用、计时等待、数据库操作或 Webhook 投递。

### 8.2 截止时间建议

第 N 次共享失败后的候选时间：

```text
candidate = 失败结算时刻 + RetryDelay(config, N)
RetryNotBefore = max(已有 RetryNotBefore, candidate)
```

故障转移达到冷却阈值后：

```text
允许探测时间 = max(RetryNotBefore, 已有或新设的成员冷却截止时间)
```

同一请求的本地重试截止时间如果仍保留，应与共享截止时间取较晚值。避免先完整等待本地间隔，再完整等待共享间隔，造成重复等待。

每次被 `Changed` 唤醒后都重新判断绝对截止时间，通知本身不是提前发送的许可。新请求、同成员恢复探测和请求 ID 变化不能把共享指数退避重新从 1 开始。

沿用 `RetryDelay` 和 `secondsToDuration` 的正间隔及溢出处理。固定模式保持原有配置边界；指数模式遵守现有最大间隔。第一阶段无需新增 jitter 配置。

### 8.3 HTTP 层行为

对于未提交且正在等待成员恢复的请求，建议沿用现有挂起等待、支持取消的模式，不主动创建新的快速 503 循环。

单个请求按现有预算确实需要结束时，继续使用 `rejectUpstream`。`Retry-After` 应与该成员剩余共享等待和适用的请求重试间隔一致，按秒向上取整，至少为 1 秒。

已提交的流不能再修改 HTTP 状态码或补一个有保证的 `Retry-After` 响应头。保护必须在下一次入站请求的发送准入处执行，不能依赖客户端理解错误事件或遵守重试建议。

## 9. 遥测、通知和脱敏

### 9.1 共享快照

共享状态需要提供可读取的快照和变化通知，至少让通知消费者获取成员身份、连续失败数、故障期、最后错误及下一次允许时间。

不要通过扫描已结束的请求列表计算共享故障，也不要在每次新请求开始时从上一条请求复制计数。日志有裁剪和清空行为，多请求并发也没有唯一的“上一条”。

最小实现可以在 Relay 内提供健康快照与通知，供 Webhook 使用；等待请求继续通过现有 `Retrying`、`NextRetryAt`、`ChannelStatusWaiting` 展示等待。`NextRetryAt` 在时间已知时应体现实际共享截止时间。

`RequestState.ErrorCount` 与 `GroupRuntime.ErrorCount` 保留原有请求含义。如果需要在现有 API 中暴露共享数，使用新增、明确命名的字段并注明对应的成员 ID，不能把旧字段悄悄改成全局累计。独立前端展示不是第一阶段前置条件。

快照和订阅注册要避免读取快照与建立订阅之间的丢事件窗口。慢消费者重连后，仍能从共享状态看到当前持续故障；请求历史是否还保留不应影响结果。

### 9.2 手动模式 Webhook

- 按当前手动成员的共享连续失败数与现有阈值比较。
- 多个请求各失败一次，也能触发一次失败通知。
- 新请求开始、正在等待、旧请求结束不会使告警状态清零。
- 同一个故障期达到阈值后只通知一次；真正恢复后通知一次恢复。
- 告警的 `FailureStreak` 使用共享数；`RetryCount` 继续按字段约定表达关联请求的重试次数，不能用 `FailureStreak - 1` 冒充。
- 切换手动成员或更换有效配置身份后，旧通知状态不能压制新成员的告警。配置变更本身不能冒充上游恢复事件。

不能只在 `observeRequest` 里再创建一个按分组累计的 map：那会让通知状态与实际准入状态各自计算，且仍受请求流丢失、重连和历史裁剪影响。通知应消费 Relay 的权威共享状态。

### 9.3 故障转移 Webhook

先保证提交后的流错误能推动成员进入共享冷却，继续使用现有失效成员阈值和字段。

目前 `observeRoute` 通过 `deadline > now` 统计冷却成员，时间经过后数字可能下降。建议恢复通知增加“收到有效完整成功确认”的条件：冷却到期只是允许探测，不能仅凭时间经过或开始探测发送恢复通知。

通知消费者需要能观察到这次完整成功确认。当前 `recordRouteSuccess` 对普通当前成员可能不发布路由变化；新增结算流程应提供带版本的成功确认或等效状态，不能假定每次成功都会自然产生既有路由事件。重连快照也要能区分“已经确认恢复”和“只是冷却到期”。

此处应保留现有冷却成员数的统计口径，补充恢复触发资格；如果改为统计所有未恢复成员，需要作为另一个明确的语义变更说明。现有 Webhook 测试把过期冷却直接作为恢复前提，实施时需要按最终约定调整其断言。

### 9.4 非阻塞与脱敏

Relay 的共享状态写入和发送准入不能等待 Webhook 网络投递。复用现有有界队列、异步 worker 和通知失败处理。

共享 `LastError` 在写入快照、日志或通知前必须脱敏，沿用 `privacy.Redactor` 及现有通知脱敏逻辑。不能在新增 map、日志或通知字段里存储并公开凭据、私有连接参数或请求会话标识。测试使用虚构值和本地 `httptest` 服务。

### 10.1 文件范围

| [route.go](../internal/relay/route.go)，必要时新增共享健康状态文件 | 共享计数、退避、恢复资格、配置版本与快照通知；复用已有冷却 |
| [state.go](../internal/relay/state.go) | 按尝试去重，保持请求计数语义，发布共享等待带来的请求进度 |
| [retry.go](../internal/relay/retry.go) | 优先直接复用；仅在绝对截止时间计算确有需要时增加局部辅助逻辑 |

| [runtime.go](../internal/relay/runtime.go) | 仅在需要对外附加健康遥测或复用订阅机制时调整，保持旧字段含义 |
| [channel_concurrency.go](../internal/relay/channel_concurrency.go)、[channel_refresh.go](../internal/relay/channel_refresh.go) | 核对排队期间失效、恢复资格和配置刷新协作；根据必要性局部修改 |
| [service.go](../internal/webhook/service.go) | 订阅共享健康状态，修改手动阈值来源，补充恢复确认及重连逻辑 |
| 相关 Relay、Webhook 与 server handler 测试 | 补齐真实请求、并发、通知和配置生命周期验证 |

文件表是影响地图，不要求每个列出的文件都修改。实现者应按实际数据流选择最小清晰的落点。

### 10.2 实施步骤

1. **核对基线。** 以第 1 节记录的 `test` 分支提交为基础，阅读第 3 节涉及函数；如有后续提交或未提交改动，先核对相关差异，确认是否已有部分修复，并记录实际起点及需要保留的旧行为。
2. **建立行为复现。** 用本地 SSE 上游构造前导事件后报错及内容后报错，再从客户端创建多个独立请求，观察现有调用次数、请求终态和告警条件。
3. **实现共享状态和准入。** 先定义作用域、版本、恢复资格、退避截止时间和生命周期，验证手动及故障转移分支。
4. **接入完整结果结算。** 对所有真实发送的上游尝试统一结算，补齐提交后错误、完整成功、取消和去重。
5. **接入通知和等待遥测。** 使相同共享状态驱动准入和告警，补齐启动、重连、配置切换。
6. **完成针对性回归。** 按第 11 节验收，再执行第 12 节检查。
7. **形成交付说明。** 说明实际变更、配置行为、验证结果及未覆盖边界，明确第二阶段是否仍未实施。

不要在共享状态尚未接入发送准入时就把修复标为完成；也不要仅把某个错误字符串加入重试列表就结束工作。

## 11. 必要验收场景

### 11.1 核心行为

| 编号 | 场景 | 必须满足 |
| --- | --- | --- |
| A1 | Responses 连续返回 `response.created → response.in_progress → error`，客户端每次新建 HTTP 请求 | 请求 ID 不同，各请求错误数按自身累计；共享错误数持续增加；后续上游调用遵守间隔 |
| A2 | 每次先输出真实内容，再返回完全相同的流错误 | 当前响应不拼接另一次生成；共享故障累计；同一流错误只计一次 |
| A3 | 首事件就是错误 | 原请求仍可按现有逻辑重试，同时正确维护共享状态，没有双重等待或双计数 |
| A4 | 同一请求两轮产生相同文案，第二轮在提交后失败 | 两次真实失败分别计入请求和适用的共享计数，终态处理不会再重复加一 |
| A5 | 手动模式持续故障，每个客户端请求只失败一次 | 共享退避和通知阈值不随新请求重置，达到阈值通知一次 |
| A6 | 手动模式有有限尝试预算，新请求到达时成员已有多次历史失败 | 新请求等待共享准入后仍拥有自己的尝试预算；等待不消耗预算 |
| A7 | 故障转移成员跨多个请求达到阈值 | 原成员进入冷却；后续请求可选备用成员；已提交失败响应本身不重放 |
| A8 | 所有成员冷却 | 等待最早允许探测时间；状态唤醒不产生忙循环 |
| A9 | 固定与指数模式、较大间隔配置 | 固定间隔保持固定；指数退避跨请求累计并封顶；时间计算不因溢出退化为立即重试 |

### 11.2 并发与生命周期

| 编号 | 场景 | 必须满足 |
| --- | --- | --- |
| B1 | 多个请求同时等待同一个故障成员 | 截止时间前无新上游发送；到期后只有允许的恢复探测取得资格 |
| B2 | A 失败后，在故障前发出的 B 迟到成功 | B 不清除 A 造成的保护；有效探测成功后才恢复 |
| B3 | 一个恢复探测完整成功后，旧故障过程的请求迟到失败 | 原请求保留历史错误，共享健康不被旧结果重新污染 |
| B4 | 探测只收到首帧，然后失败 | 首帧不放开所有等待者；故障继续累计 |
| B5 | 请求在共享等待、渠道容量排队、流读取中分别取消 | 及时退出、归还资源；不把取消算成渠道故障，不清零已有故障 |
| B6 | 排队时另一个请求确认故障 | 排队请求发送前重查健康，不能使用早先的健康快照绕过退避 |
| B7 | 更换成员、渠道配置或删除分组后旧结果返回 | 旧结果不改变新配置的健康状态；旧等待者被正确唤醒 |
| B8 | 清空请求历史或请求记录被裁剪 | 共享故障、等待和告警状态保持有效 |
| B9 | 容量不足导致探测让出，或配置变化时放弃未发送尝试 | 不增加上游失败，不消耗请求尝试预算，资格正确归还 |
| B10 | 正常健康成员有并发请求 | 保留正常并发能力，未被健康保护无条件串行化 |

### 11.3 协议、成功确认和通知

| 编号 | 场景 | 必须满足 |
| --- | --- | --- |
| C1 | 正常完整流和合法空输出成功终态 | 能成功结束；具备资格时恢复，不能要求必须有文本 |
| C2 | 流没有成功终态就 EOF，且解码器无底层错误 | 按真实协议及转换路径确认异常后记为失败，不能错误恢复 |
| C3 | 客户端写失败或主动中止 | 请求交付结果与上游健康归因正确分开 |
| C4 | 同协议透传和跨协议转换分别发生提交后错误 | 两条路径都进入统一结算，不能只覆盖 Responses 透传 |
| C5 | 通知消费者处理同一快照多次或慢消费者重连 | 持续故障可从共享状态恢复；同一故障期不会重复通知 |
| C6 | 达阈值告警后冷却到期，但探测尚未完整成功 | 不因时间经过或首帧单独发送恢复通知 |
| C7 | 完整恢复后再次发生新一轮连续故障 | 清晰形成新的故障期，能够再次通知 |
| C8 | 错误事件含虚构的敏感字符串 | 请求诊断、共享快照、日志、通知均通过现有脱敏约束 |
| C9 | 未提交请求达到预算后最终失败 | 503 与协议错误格式兼容，`Retry-After` 覆盖适用的共享剩余等待 |

### 11.4 测试实现提示

复用 [testsupport_test.go](../internal/relay/testsupport_test.go) 的临时 SQLite、本地上游和渠道构造。现有 `newRelayEngine` 只挂载 Chat Completions；Responses 测试必须显式挂载 `Forward(llm.APIFormatOpenAIResponse)` 或扩展测试辅助函数。

真实客户端请求测试需要检查上游调用次数、时间下界、响应内容、终态和通知，不能只调用 `recordFailure` 再断言计数加一。共享状态的边界测试可采用现有 `pickGroupItemAt`、`recordRouteFailureAt` 一类可传入时间的设计，避免为了测试几十秒冷却而真实等待。

并发测试用通道或屏障控制 A、B、C 的完成顺序，验证实际准入和资格释放；避免靠很短的 Sleep 猜测时序。所有可能阻塞的测试都要有超时及上下文清理。

保留或适配现有 `TestStreamingDoesNotFailoverAfterFirstEventCommit`：它要求同一个已提交请求不再调用第二成员；新增下一次独立请求遵守共享路由状态的验证。既有“本请求不重放”的断言仍然成立。

## 12. 实施后的检查命令

在仓库根目录执行相关包测试和静态检查：

```powershell
go test ./internal/relay ./internal/webhook ./internal/server/handlers -count=1
go vet ./internal/relay ./internal/webhook ./internal/server/handlers
git diff --check
```

本次涉及共享状态和并发控制，还应执行：

```powershell
go test -race ./internal/relay ./internal/webhook -count=1
```

如果当前 Windows 工具链不支持 race，记录具体失败原因，在现成支持的环境补跑；不能把未执行写成通过，也不要为跑检查擅自安装依赖或修改环境。

如果最终触及公共配置、通知对外契约或其他包调用关系，按实际影响完成仓库规定的全量检查。检查计划应在实施范围明确后一次确定，避免无变化反复运行相同测试。仅当修改了前端时才执行前端 lint、类型检查和构建，并按仓库约定选择构建输出目录。

当前相关测试的 `TestMain` 会创建临时 SQLite 并初始化测试环境。运行前复核最新测试代码，使用测试临时数据；本文编写期间没有运行这些命令。

## 13. 第二阶段：延后流式响应提交

第二阶段的目标是将如下场景留在原请求的重试循环：

```text
response.created → response.in_progress → error
```

建议识别并暂存协议明确允许的前导元数据，首次可交付内容或合法成功终态到达时，再按原顺序一次提交缓存并继续转发。失败时丢弃本轮尚未提交的缓存，进入已有重试结算。

实施时需要另行明确：

1. **事件分类。** 文本、工具调用、工具参数、推理内容、音频等均需考虑；不能仅用文本非空作为允许提交的条件。
2. **副作用边界。** 上游或客户端工具已经开始执行时，不能因为没有文本输出就认为可安全重放。
3. **未知事件。** 未识别事件采用保守策略，不随意丢弃或重排。
4. **缓存上限。** 限制字节数、事件数和等待时间；超过上限应有明确结果，不能无限积累。
5. **超时语义。** 区分收到首个协议事件和收到可交付结果；前导事件不能无限延长等待。
6. **HTTP 提交边界。** 预提交阶段不能提前写响应体、Flush 或发送 SSE 心跳，否则无法保持同一个 HTTP 响应内的重试能力。
7. **协议一致性。** 缓存释放时保留事件顺序、ID 和关联字段；同协议和跨协议路径分别验证。
8. **合法空结果。** 没有文本但收到有效成功终态时也能完成。

第二阶段需要独立测试，不与第一阶段验收混在一起。第一阶段的共享故障保护在第二阶段完成后仍有必要，因为已经输出内容后的错误仍可能导致客户端重发。

## 14. 交付说明模板与完成标准

实施会话的最终交付应说明：

- 实际修改文件及关键行为，特别是共享保护作用域和复用 `member_max_attempts` 的新增条件。
- 请求内计数、共享连续失败、退避和恢复探测的实际规则。
- 提交后失败如何结算，如何避免重复计数、旧请求错误恢复和发送竞争。
- 手动及故障转移告警的数据来源、去重与恢复条件。
- 第 11 节核心场景和检查命令的执行结果；失败或未执行项如实列出。
- 第二阶段是否仍待实施，以及本次实现中新增的兼容边界。

第一阶段只有在“多次独立请求持续失败 → 共享累计 → 服务端限制下一次发送 → 达阈值可通知 → 有效完整成功后恢复”整个链路通过验证后，才算完成。

服务端能约束发往上游的请求频率，无法保证外部客户端停止创建 HTTP 请求。第一阶段状态为进程内、按分组成员共享；正常请求初始并发、跨进程协同以及客户端自身的业务重试预算应分别理解。

持续长流在首帧后既不结束也不报错的情况，需要专门的流空闲或总时限设计。第一阶段至少保留上下文取消和所有资源释放路径，不因本方案擅自给正常长流增加未经约定的总时限。
