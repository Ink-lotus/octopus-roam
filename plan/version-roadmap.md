# Octopus Solo 产品版本路线图

本文档是当前产品线的版本入口。旧的 `v1.0plan.md` 和 `phase*.md` 保留为上游二开阶段的历史契约与验收记录；新的功能开发按本文档的里程碑序列推进。

当前基线：`test` 分支已经通过提交 `04f43e7` 回退阶段 6 的 companion 状态 Token、状态快照和状态 SSE，阶段 6 原提交 `1210f74` 仍保留在 Git 历史中。Webhook、故障转移状态机、运行时状态和阶段 5 过滤功能继续作为产品基线。

这一基线将由 `S1` 上游同步替换。`S1` 完成后，各里程碑文档声明的基线一律以 `S1` 建立的 commit 为准，开工前用 `git rev-parse HEAD` 复核。

### 执行顺序

`S1` → `M1` → `M2` → `M3` → `R1`。

`S1` 必须在 `M1` 之前完成。`S1` 的 U3 要手工移植 `internal/relay/state.go` 和 `internal/relay/handler.go`，而 `M1` 的 V010-02 和 V010-03 改的是同一对文件。先做 `M1` 会让手工移植叠在未经验证的改动之上，出问题时无法区分行为变化来自依赖升级还是来自移植。

`M2` 的 V020-01（日志置顶与筛选）不依赖本里程碑其他任务，可以先做。V020-02 的公共刷新服务是 `M2` 的枢纽任务，V020-03、V020-05、V020-06 以及 `M3` 的 V030-02 都依赖它，必须先完成。

## 贯穿所有里程碑的产品约束

1. 分组模式由每个分组单独保存。全局路由策略只修改 Relay 参数，不批量修改 `manual`/`failover` 模式。
2. 全局默认策略不勾选覆盖时只影响新建分组；勾选覆盖时修改已有分组的策略参数，同时保留分组模式、成员、顺序和手动选择成员。
3. 渠道刷新成功后，渠道模型和授权以本次结果为准；失效授权对应的分组成员会被清理，已有分组实体不会被创建、删除或重建。
4. 分组自动添加只处理已有分组。关键词匹配和严格匹配按分组配置决定，严格匹配不会把 `claude-opus-5-5` 加入 `claude-opus-5` 分组。
5. 上游模型请求全部成功后才提交刷新结果；成功的空列表可以保存为零模型；任一 Key 失败时保留旧状态。
6. companion 暂不纳入产品版本。监控继续使用 Webhook 和现有管理端 SSE；未来重新启动 companion 时再设计独立消费接口。
7. 版本文档中的文件路径是当前代码事实和预计改动范围。执行任务前必须重新读取文件，发现结构变化时以代码为准并在汇报中说明。

## 对外版本号规则

本项目的版本线自 `v0.1.0` 独立起算，**不跟随上游编号**。上游基线是 bestruirui/octopus v0.13.6；README 和首个 Release Notes 必须写明 fork 来源与独立编号，避免 `v0.13.6` → `v0.1.0` 被误读为降级。

仓库内已有三条互相独立的版本线，各自记账：

| 线 | 当前值 | 职责 |
| --- | --- | --- |
| 迁移编号 | `internal/db/migrate/013.go` | 数据库结构第几次变更 |
| 备份格式 | `internal/op/backup.go` 的 `dbDumpVersion = 1000`，加密容器版本 `1` | 产品内容格式与加密容器各自演进 |
| 对外版本 | `main.go` 的 `// Version` 注释 | 用户能否安全升级 |

前两条已经精确记录改动次数，因此对外版本号不承担计数职责，只回答「用户能否安全升级」。这也是它可以走得比里程碑慢的原因。

R1 已通过 `product: "octopus-solo"` 和内容版本 `1000` 隔离备份身份。无标识只接受已审计的上游 `0`/`5`；无标识 `6` 明确拒绝。导出增加口令加密容器，内容版本不因加密容器版本而混用。见[身份设计](../docs/superpowers/specs/2026-09-26-backup-format-identity-design.md)与[加密设计](../docs/backup-encryption-design.md)。

### 强制升 minor 的判据

满足任一条即必须升 minor（`v0.x.0`），不得作为 patch 发布：

1. `dbDumpVersion` 递增。导入校验只接受特定版本，递增后旧版本程序无法导入新备份，用户失去降级回滚能力。
2. `internal/db/migrate/` 新增编号文件。数据库结构已变，回滚需要手工处理。
3. 新增公开 API 路径，或以破坏兼容的方式改变已有请求/响应结构、枚举值。纯新增可选字段不触发。
4. 已有配置字段的默认值或语义变化。影响无人值守的镜像升级。
5. 移除或改名任何用户可见配置。
6. 依赖升级导致 Transformer、Relay 或协议转换的可观察行为变化。仅版本号变动、无行为差异的升级不触发。

其余改动走 patch（`v0.1.x`）：bug 修复、性能优化、界面与交互调整、文案与三份 locale、纯新增且默认关闭且不触碰 schema 与备份格式的可选配置。

判据决定下限，攒批决定上限：可以把多个触发判据的功能攒成一个 minor 一起发，但不能把其中任何一个塞进 patch。已知会触发判据的规划项——生图触发 #3，管理界面优化触发 #1 和 #2，WebSocket 触发 #3。

### 版本递进的判定条件

| 目标 | 条件 |
| --- | --- |
| `v0.1.0-rc.1` | `S1` 与 `M1`～`M3` 全部验收通过；产品主分支已切换为 `main`，已修的 `release.yaml` 在其上生效 |
| `v0.1.0` | `R1` 全量回归全绿；上游 `0`/`5` 与本产品加密备份恢复成功，无标识 `6` 明确拒绝；跨数据库验收完成；无 P0/P1 遗留 |
| `v1.0.0` | 连续两个发布周期无 breaking change（API、配置字段、备份格式）；升级与回滚路径有文档且实测通过 |

条件不满足就继续停在 `0.x`，不用形容词代替判定。

## 分支与发布规则

- `S1`、`M1`～`M3` 全程不修改 `main.go` 的版本注释，不产生标签，不触发发布。
- `release.yaml` 在 push 到 `main` 且 `main.go` 变化时，会自动打标签、推送远程、创建 GitHub Release 并按需覆盖 Docker `latest`。因此**修改 `main.go` 的版本注释本身就是一次对外发布操作**，必须单独授权，不能当作普通文档改动处理。
- `release.yaml` 原有的三处问题已修复：预发布按版本号中的连字符自动判定、预发布不覆盖 Docker `latest`、触发分支由 `master` 改为 `main`。`master` 保留为上游同步分支且不再触发发布，上游的版本号提交同步进来不会误发。
- **`R1` 先切分支再发 rc**：创建 `main`、确认已修的 `release.yaml` 在其上生效、切换默认分支，然后才修改 `main.go` 发 `v0.1.0-rc.1`。这样 rc 与 GA 走完全相同的发布路径，rc 才真正验证了流水线；反序会让 GA 执行一条 rc 从未验证过的配置，且 rc 期间 `master` 会同时是发布触发器和上游同步落点。
- `v0.1.0` 不等待生图、管理界面优化和 WebSocket，这些进入后续能力包。
- 修改分支、标签、远程仓库、数据库结构或发布内容前，执行会话必须单独确认授权；版本文档只定义目标，不代替执行授权。

## 单功能任务的定义格式

每个任务只实现一个可验收功能，依赖排序、集成和里程碑验收由执行会话负责。任务 ID 沿用各里程碑文档内已有的编号，不重新编号：`Ux` 属 `S1`，`V010-xx` 属 `M1`，`V020-xx` 属 `M2`，`V030-xx` 属 `M3`，`V100-xx` 属 `R1`。开工前按下面的结构把任务写清楚：

```text
任务 ID：<里程碑>/<文档内编号>，例如 M1/V010-02
产出定义：完成什么功能；具体 API、界面或数据行为；验收标准。
材料位置：当前代码和相关计划文档的具体路径。
改动边界：允许修改的文件/区域；明确不触碰的其他功能。
必要检查：必须运行的测试、lint、构建或人工检查。
```

本路线图不指定子代理和模型档位。是否派发子代理由用户在执行时决定；未经点名时按全局规则处理。

每个任务完成后必须报告：修改文件、接口和数据结构变化、迁移与兼容策略、测试命令及结果、尚未解决的问题。后端任务先完成并通过 Go 检查，再进行前端任务；不得顺带重构无关模块或新增未记录的依赖。
