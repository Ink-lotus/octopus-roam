# 确定性隐私保护规则管理实现方案

状态：已实现并完成验收。实现范围、检查结果和性能对比见[实施验收记录](privacy-rule-management-implementation.md)。本文保留方案制定时的现状说明，作为实施前基线。

编写日期：2026-10-08。代码检查基线：`05c46b2`；实施前重新核对工作区与相关代码。

## 1. 目标与已确认的设计

将“确定性隐私保护”从系统设置中的单行开关提升为独立卡片，提供可查看、可逐条启停的内置规则，以及可添加、编辑、启停和删除的自定义规则。用户遇到误脱敏时，可以停用对应规则，并通过预览确认实际命中的规则。

本方案采用以下界面结构：

- 卡片标题直接使用“确定性隐私保护”。
- 标题下方注明“实验性功能”，配一段简短的作用范围说明。
- 标题右侧提供“添加规则”和“查看全部规则”图标按钮，沿用 API 密钥、Webhook 通知的样式。
- 卡片内包含功能总开关和固定高度的规则列表。
- 放大后打开专门的规则管理面板；内置规则提供详情入口，自定义规则提供编辑入口。

| 规则来源 | 查看详情 | 启用 / 关闭 | 修改名称与匹配内容 | 删除 |
| --- | --- | --- | --- | --- |
| 内置规则 | 支持 | 支持 | 不支持 | 不支持 |
| 自定义规则 | 支持 | 支持 | 支持 | 支持 |

内置规则初始全部启用。功能总开关沿用现有偏好，新安装默认关闭。总开关关闭时仍可管理和预览规则，各规则的启停配置分别保存。

## 3. 卡片与交互

### 3.1 设置页卡片

新增 `web/src/components/modules/setting/Privacy.tsx`，导出 `SettingPrivacy`。卡片放在设置页右列、日志设置之后，使诊断相关设置相邻。

布局示意：

```text
盾牌  确定性隐私保护                         [+] [放大]
实验性功能
对请求诊断、错误信息和通知中的敏感内容进行确定性脱敏。

启用隐私保护                                  [总开关]

规则                                      已启用 X / Y
[开关] 已知凭据                 内置             [详情]
       遮蔽请求中已知的密钥和自定义 Header 值
[开关] 客户编号                 自定义           [编辑]
       字段名 · customer_id                     [删除]
```

视觉沿用 `rounded-3xl`、`border-border`、`bg-card`、`p-6` 和现有图标按钮尺寸。标题与说明属于同一张卡片，列表使用普通行布局。

紧凑列表沿用 API 密钥、Webhook 的 `h-36` 滚动区域。规则名称和摘要支持省略，详情或编辑面板展示完整内容。内置规则按固定顺序排列，自定义规则按创建顺序追加；修改名称或启停状态不改变位置。

总开关关闭时展示“总开关已关闭，规则暂未生效”，逐条开关仍表达已保存的配置。“已启用 X / Y”统计规则配置，总开关状态单独表达。

### 3.2 查看全部规则

复用现有 `MorphingDialog` 的展开方式，面板宽度参考 `max-w-2xl`，高度受视口约束。标题、说明、总开关和添加按钮固定，规则区域滚动；移动端保留边距并允许标题和操作区换行。

紧凑卡片和展开面板共用查询缓存、规则行组件及操作函数。保存成功后两处立即显示服务器返回的最新状态。

详情和编辑弹层复用现有 Radix Dialog 方案。处理好嵌套弹层的 Escape、点击外部、焦点约束与关闭后焦点恢复：编辑表单打开时，Escape 先关闭表单，返回规则列表。

### 3.3 内置规则详情

展示名称、固定规则 ID、匹配对象、识别方式、适用范围、示例与启停状态。内置名称和说明来自三份 locale；规则 ID 供识别与问题反馈使用。

详情提供启停和样例预览。前端按规则来源展示操作，后端同样限制内置规则只能切换 `enabled`。

### 3.4 自定义规则表单

首版字段为规则名称、匹配类型、匹配内容、启用状态，以及样例输入与脱敏预览。名称必填；新建规则默认启用，实际生效同时受总开关控制。

| 匹配类型 | 首版语义 |
| --- | --- |
| 字段名 `field_name` | 忽略大小写的完整字段名匹配，覆盖 JSON 对象键、Header 名、URL 查询参数和文本中的字段赋值；脱敏对应值 |
| 固定文本 `literal` | 大小写敏感的字面量子串匹配；匹配内容中的空格和标点按原样保存 |
| 正则表达式 `regex` | 使用 Go `regexp` 支持的语法，对命中的完整文本片段进行脱敏 |

字段名规则针对对象中的每一级键名匹配；首版使用字段名本身，不增加 JSONPath。用户显式添加的字段规则优先表达用户意图，例如可以主动匹配内置规则豁免的 `api_key_name`。

固定文本和正则处理诊断文本、结构化内容中的字符串值，以及解析后的 Header / URL 值。JSON 的结构、普通数字精度和未命中内容应保留。正则不提供捕获组替换模板，所有命中统一使用现有确定性掩码。

表单采用显式保存。保存失败保留草稿，字段错误在对应输入下展示。启停直接保存，操作期间显示忙碌状态；删除自定义规则沿用现有条目删除确认方式。

## 4. 内置规则目录

首版从现有执行环节拆出以下七条规则。ID 是固定协议标识，名称可本地化；各条均默认启用。

| 固定 ID | 界面名称 | 对应行为与关闭边界 |
| --- | --- | --- |
| `builtin.known_credentials` | 已知凭据 | 从渠道密钥、模型探测凭据和已解析的自定义 Header 配置中显式收集值；关闭后停止这类配置值的收集与派生别名注册 |
| `builtin.sensitive_headers` | 敏感请求头 | 根据敏感 Header 名收集值，包含 Cookie 值与 Basic 编码中派生出的凭据；关闭后停止该来源的全部收集 |
| `builtin.url_userinfo` | URL 用户信息 | 识别 URL 中的用户名、密码及对应编码形式；关闭后停止识别、收集和 URL 对应位置的遮蔽 |
| `builtin.url_query` | URL 敏感参数 | 根据敏感参数名识别查询值；关闭后停止参数识别、收集和对应值的遮蔽 |
| `builtin.auth_text` | 认证文本 | 识别非结构化文本中的 Bearer / Basic 凭据片段；关闭后停止文本识别及凭据注册 |
| `builtin.text_fields` | 文本敏感字段 | 识别文本中形如敏感字段赋值的内容，包含带引号和转义的值；关闭后停止该文本解析规则 |
| `builtin.json_fields` | JSON 敏感字段 | 递归识别结构化敏感键，保留现有元数据例外和重复键处理能力；关闭后停止按这些键识别、收集和替换 |

`Add()`、`replaceKnown()`、URL 解析和 JSON 遍历是多个规则共用的机制。实施时将“发现敏感值”和“记住并替换该值”的来源关联起来，例如内部使用 `Register(ruleID, value)`。`known_credentials` 只控制显式配置值来源，不应控制其他规则共用的整个替换器。

同一值可以具有多个启用来源。关闭其中一条后，其他实际命中的规则仍可以脱敏该值；预览应显示这些来源。关闭全部内置与自定义规则后，新的诊断实例返回原文，不进行敏感值收集或仅由脱敏引入的格式改写。

URL 解析失败、异常查询串和 JSON 解析回退也必须归属明确规则。URL 整体解析失败时的保守遮蔽归入 `builtin.url_userinfo`，查询串解析失败时的保守遮蔽归入 `builtin.url_query`，详情说明这两种异常格式行为。对应规则关闭后，剩余文本处理使用同一策略快照。针对异常格式补充独立关闭用例，确保回退路径也遵守配置。

## 5. 配置模型与保存语义

### 5.1 持久化结构

复用 `Setting` 表，保留现有 `privacy_protection_enabled`，新增 `privacy_protection_rules` JSON 设置。设置默认值通过现有缺失设置补齐流程写入。

建议结构如下，示例中的自定义条目仅用于说明格式，新安装的 `custom_rules` 为空数组：

```json
{
  "version": 1,
  "revision": "<服务器生成的修订号>",
  "builtin_enabled": {
    "builtin.known_credentials": true,
    "builtin.sensitive_headers": true,
    "builtin.url_userinfo": true,
    "builtin.url_query": true,
    "builtin.auth_text": true,
    "builtin.text_fields": true,
    "builtin.json_fields": true
  },
  "custom_rules": [
    {
      "id": "custom_<服务器生成的 ID>",
      "name": "客户编号",
      "kind": "field_name",
      "pattern": "customer_id",
      "enabled": true
    }
  ]
}
```

内置定义在代码中维护，数据库只保存其启停状态。自定义 ID 由服务端生成并保持稳定，名称修改不改变 ID。`revision` 是独立于掩码的配置修订号，每次规则写入或导入后更新，用于拒绝旧页面覆盖新配置。

配置类型、内置目录和纯校验逻辑放在 `internal/privacy`，避免该包依赖数据库或 `model`。`model.Setting.Validate()`、op 层及导入路径调用同一校验器。

### 5.2 校验与容量

首版将限制集中为后端常量，并由读取接口返回给前端：

- 最多 64 条自定义规则，规则名称最多 80 个 Unicode 字符。
- 匹配内容非空，最多 1024 字节；字段名按完整名称校验，固定文本和正则保留原始内容。
- 规则配置序列化后最多 128 KiB；预览输入最多 32 KiB，已知值样例最多 16 个且计入请求总量限制。
- 校验版本、字段类型、重复 ID、内置 ID、规则类型及布尔值；写入接口拒绝未知字段和客户端提供的内置定义。
- 正则在保存前编译，拒绝非法语法与可能产生零长度匹配的表达式；零长度检查使用 `regexp/syntax` 的表达式结构，执行时也跳过空匹配。

使用 Go 标准库正则，使预览与实际执行共用语法和匹配机制。现有 `RegexFilterField` 面向 ECMAScript，包含负向前瞻示例；隐私规则表单应采用适配 Go 语法的提示和服务端校验。

### 5.3 原子发布与并发

规则写操作在 op 层统一完成以下步骤：读取当前配置、核对修订号、应用单条操作、校验并编译候选配置、持久化、更新缓存、发布新的不可变策略快照。任一步失败均保留原来的有效配置。

总开关写入、规则写入、备份导入与缓存重载使用一致的同步顺序。数据库更新以原配置值作为比较条件，冲突返回 `409`；避免两个页面或展开面板覆盖彼此的修改。

总开关继续支持现有 `/setting/set`，其保存也通过同一发布逻辑合成 `enabled + compiled rules`。新规则键的常规写入走专用规则操作接口，通用字符串或整数设置入口不能绕过规则权限与校验。

首次加载补齐缺失内置项为启用状态，保留已有显式关闭项。非法配置不得被悄悄替换成空规则或全关闭状态：在线更新拒绝写入；启动和缓存重载返回明确错误，已经运行时保留最后一个有效快照。

## 6. 规则执行与确定性

`NewDiagnostic()` 在创建时一次性读取总开关与已编译规则，后续处理使用同一快照。请求开始后的规则修改只影响新实例；运行中的请求和诊断正文缓存继续使用它们各自的 Redactor。

Webhook 在事件准备时建立策略快照，后续事件诊断、队列处理、模板渲染与投递重试复用该快照。当前 `redactConfiguredError()` 与 `Render()` 会分别创建实例，实施时需传递同一实例或已明确处理状态的事件，避免一次通知中途切换规则。模板校验和测试通知分别使用临时实例。

执行约定：

1. 规则仅在自己的启用条件满足时识别内容并登记敏感值，登记记录包含来源 ID 和匹配语义。
2. 在替换前完成必要的识别。结构化内容先收集再遮蔽，覆盖重复键、嵌套对象，以及后出现的敏感字段在前面被回显的情况。
3. 字段规则保留字段名并遮蔽值；固定文本与正则遮蔽实际命中的文本片段。敏感值的 URL / JSON 编码别名沿用同一原值的掩码。
4. 重叠文本命中按起点、最长匹配、固定规则顺序确定替换结果，避免遍历顺序改变输出。同一位置的重复命中合并替换，预览保留各命中来源。
5. 固定文本的短字符串仍按用户指定的字面量语义处理；内置短凭据的边界匹配逻辑按原职责保留。
6. 已有 `[redacted:…]` 标记受到保护，自定义规则也要保持重复脱敏的幂等性。

掩码继续使用现有进程内 HMAC 密钥：同一进程内同一原值的输出稳定，重启后可能变化。掩码算法不作为用户可编辑字段。已生成的脱敏记录不会因规则关闭恢复原文，历史请求的快照也不会被新配置替换。

规则在配置发布时编译，请求路径复用编译结果。保留现有凭据版本与诊断正文缓存；启用规则为空时走原文快速路径。诊断正文匹配继续在 Relay 全局状态锁之外执行。

## 7. 管理与预览接口

在现有设置路由组下增加接口，沿用 `middleware.Auth()`、JSON 校验和响应格式。

| 方法与路径 | 请求要点 | 行为 |
| --- | --- | --- |
| `GET /api/v1/setting/privacy-rules` | 无 | 返回修订号、带固定元数据的内置条目、自定义条目和容量限制 |
| `POST /api/v1/setting/privacy-rules` | `revision`、`action` 和对应字段 | 执行 `create`、`update`、`toggle` 或 `delete`，成功后返回完整规则快照 |
| `POST /api/v1/setting/privacy-preview` | 输入类型、样例、预览模式、候选规则 | 使用同一规则执行器返回脱敏结果与命中来源 |
| `POST /api/v1/setting/set` | 现有总开关键和值 | 更新总开关，保留逐条规则配置 |

规则操作约定：`create` 接受自定义规则表单，`update` 接受自定义 ID 与表单，`toggle` 接受内置或自定义 ID 与 `enabled`，`delete` 只接受自定义 ID。每种操作使用明确的请求结构，服务端拒绝对内置条目的更新和删除。

示例：

```json
{
  "revision": "<读取接口返回的修订号>",
  "action": "toggle",
  "id": "builtin.json_fields",
  "enabled": false
}
```

输入错误返回 `400`，规则不存在返回 `404`，修订号冲突返回 `409`，超过请求容量返回 `413`。前端收到冲突后刷新列表并保留未保存草稿，由用户重新检查后保存。

### 7.1 预览模式

预览支持纯文本、JSON、URL、Header 四种输入类型。Header 样例通过 JSON 对象表达；格式错误直接反馈到样例输入。

- “测试当前规则”：运行指定内置规则或自定义草稿，临时按启用状态执行，便于检查已关闭规则。
- “测试已启用规则”：运行当前启用的规则集合；编辑时可以用草稿替换对应自定义规则，按草稿的启停状态执行。

两种模式均不受功能总开关影响，界面注明“预览，不修改当前配置”。请求携带规则修订号；用户改变样例、模式或草稿后，旧预览结果标记失效，迟到的响应不能覆盖较新的结果。

“已知凭据”规则的预览使用用户输入的样例值或内置虚构示例，避免读取实际渠道密钥。预览使用临时 Redactor，样例和命中内容只用于本次计算；接口和错误日志不记录样例原文。

响应返回脱敏后的内容，以及命中规则 ID 和命中次数。命中次数按原始输入中的识别位置去重，重复遍历或同一值的重复注册不重复计数。多条规则命中时分别列出名称，以便解释关闭一条后仍然出现脱敏的原因。

只在预览时启用命中收集器；正式诊断执行不增加逐条命中日志。保存、预览和正式执行共用校验与编译函数。

## 8. 备份与兼容

现有备份已经包含设置表，新增规则随设置导出。导入前同时验证总开关和规则 JSON，检查重复设置键、版本、内置 ID、自定义 ID、规则数量和正则；校验失败时整次导入不写入数据库。

旧备份缺少规则设置时，按现有增量导入语义保留目标实例已有规则；目标也没有规则时补入默认值。旧备份已有的总开关值正常恢复。

包含规则设置的备份完整恢复对应规则集合与各启停值。成功后生成新的规则修订号，发布与数据库一致的总开关和规则快照，旧编辑页面保存时得到冲突反馈。

采用现有设置字段可容纳的 JSON 结构，首版通过 `version: 1` 管理规则配置格式。遇到不支持的新版本或未知内置 ID 时返回可定位的兼容错误。加密备份现有流程继续承载这些设置。

已有文件按接入职责局部修改：设置 model / op / handler、隐私执行器、渠道诊断凭据收集、Relay 与 Webhook 的调用点、备份导入、设置页入口、系统设置组件，以及 `zh_hans.json`、`zh_hant.json`、`en.json`。

实施分为五步，每一步先完成对应验证再进入下一步：

1. **配置与内置目录**：建立固定 ID、默认配置、校验器、编译快照和保存契约，验证旧开关与缺失设置兼容。
2. **执行器接入**：给现有收集和替换标明来源，接入逐条开关和三种自定义规则，覆盖各诊断调用点与缓存生命周期。
3. **管理、预览和备份**：完成专用接口、内置操作限制、修订号冲突处理、预览命中结果与导入校验。
4. **前端卡片**：迁出系统设置中的开关，完成列表、放大、详情、编辑、预览及三语文案。
5. **集成验收**：检查前后端行为一致、并发更新、历史请求、移动端与键盘操作，记录检查结果及实际文件差异。

阶段检查使用相应包和用例；最终检查补齐尚未覆盖的集成范围。同一代码状态下已通过的检查直接记录，只有后续修改影响该范围或发现问题时才重跑。

## 10. 验收标准

### 10.1 界面与管理

- 设置页出现独立的“确定性隐私保护”卡片，标题下有“实验性功能”；系统设置原位置不再重复展示该开关。
- 添加、放大、规则列表与 API 密钥 / Webhook 的视觉一致，小屏幕没有横向溢出。
- 内置规则全部可见、可查看详情、可启停；自定义规则完成创建、编辑、启停、删除和刷新后恢复。
- 总开关关闭时可继续配置与预览，重新打开后恢复各条已保存状态。
- 卡片和展开面板状态同步；加载、读取失败、保存失败、修订号冲突和重复提交均有明确处理。
- 表单标签、图标按钮名称、开关名称包含必要语义；键盘可以打开、操作和关闭弹层，焦点正确恢复。

### 10.2 规则执行

- 对七条内置规则分别构造隔离样例：仅开启该条时产生预期掩码，关闭后既不登记该来源，也不通过其回退路径继续脱敏。
- 用同时命中两条规则的样例验证重叠处理；逐条关闭后的输出与预览命中来源一致。
- 用 Header → 错误文本、URL → 正文、JSON 字段 → 前置回显等样例验证收集、编码别名和跨位置替换。
- 三种自定义规则覆盖短文本、Unicode、引号、转义、无匹配与重叠匹配；非法或零长度正则被拒绝。
- 全部规则关闭时，新诊断实例完整保留原文；总开关关闭时不收集敏感值。
- 验证已有稳定掩码、幂等性、JSON 重复键、精确数字、元数据例外和普通诊断上下文用例。
- 请求进行中保存规则后，旧请求与其正文缓存使用旧快照，新请求使用新快照；Webhook 单次处理保持快照一致。
- 用本地模拟上游验证认证信息与业务请求按原值发送，配置接口凭据掩码使用其独立策略。

### 10.3 持久化与接口

- 总开关和逐条规则状态经保存、缓存重载及重启恢复；保存或编译失败时旧配置仍有效。
- 后端拒绝编辑 / 删除内置规则、伪造内置定义、未知 ID、重复 ID、超限和非法配置。
- 两个页面基于同一修订号修改时，后提交的旧版本收到冲突，不覆盖已提交的修改。
- 预览与相同配置下正式执行的结果一致；预览不更改设置、正式请求状态或全局收集器。
- 备份往返恢复规则；旧备份缺失配置、非法正则、重复设置和未知版本分别覆盖；失败导入没有部分写入。

### 10.4 实施后的检查命令

在仓库根目录执行后端检查：

```powershell
go test ./... -count=1
go vet ./...
```

针对配置发布、规则收集和正文读取的并发场景，在支持 Go race detector 的现有环境执行：

```powershell
go test -race ./internal/privacy ./internal/op ./internal/relay ./internal/webhook -count=1
```

前端检查与独立临时构建目录：

```powershell
pnpm -C web lint
$privacyRulesBuild = Join-Path ([System.IO.Path]::GetTempPath()) ('octopus-privacy-rules-' + [guid]::NewGuid().ToString('N'))
pnpm -C web build --outDir $privacyRulesBuild --emptyOutDir false
git diff --check
```

三份 locale 需要解析检查和新增键一致性检查。交互验收覆盖桌面、窄屏、总开关、逐条开关、展开后编辑、预览错误和键盘焦点；当前前端没有独立测试脚本，可使用现有浏览器检查能力记录这些场景。

由于规则会进入诊断匹配路径，使用现有 `BenchmarkReplaceKnown`、`BenchmarkRedactorBody` 在相同环境比较默认配置，并补充达到规则上限时的代表性样例，记录耗时与分配。实际缺少 race 或浏览器检查环境时，将未完成项写入验收结果。

本文本身只需要检查文件内容、相对链接与差异格式；以上代码与交互检查在功能实施时执行。
