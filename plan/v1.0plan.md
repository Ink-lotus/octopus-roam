三、固定产品契约

1\. 重试计数

手动模式和故障转移成员都使用“总尝试次数”语义：

•

首次请求计为第 1 次尝试。

•

manual\_max\_attempts = 3 表示最多发起 3 次请求。

•

manual\_max\_attempts = 0 表示无限重试。

•

member\_max\_attempts 继续表示故障转移模式下单个成员的总尝试次数。

•

retry\_count 表示额外重试次数，等于 attempts - 1。

2\. 重试模式

新增：

type RetryMode string



const (

&#x20;   RetryModeFixed       RetryMode = "fixed"

&#x20;   RetryModeExponential RetryMode = "exponential"

)

GroupRelayConfig 增加：

RetryMode                    RetryMode `json:"retry\\\_mode"`

RetryInitialIntervalSeconds int       `json:"retry\\\_initial\\\_interval\\\_seconds"`

RetryMaxIntervalSeconds     int       `json:"retry\\\_max\\\_interval\\\_seconds"`

ManualMaxAttempts           int       `json:"manual\\\_max\\\_attempts"`

保留现有字段：

MemberRetryIntervalSeconds

MemberMaxAttempts

MemberNonStreamResponseTimeoutSeconds

MemberStreamFirstEventTimeoutSeconds

MemberCooldownSeconds

约定：

•

固定模式使用 member\_retry\_interval\_seconds。

•

指数模式初始间隔默认 1 秒。

•

指数倍数固定为 2。

•

最大间隔默认 600 秒，后端硬上限为 600 秒。

•

默认模式为固定模式，保持现有行为。

•

默认固定间隔沿用后端当前默认值 3 秒。

•

member\_affinity\_seconds 保留读取兼容，但不再参与故障转移。

3\. 故障转移

故障转移状态必须符合以下规则：

1\.

当前成员成功后持续使用。

2\.

只要当前成员没有失败，不切换到更高优先级或更低优先级成员。

3\.

当前成员达到自身尝试上限后进入冷却。

4\.

切换流程从分组列表第一项开始按优先级扫描。

5\.

冷却中的成员跳过。

6\.

候选成员失败并耗尽自身尝试次数后进入冷却。

7\.

找到成功成员后固定为当前成员。

8\.

全部成员处于冷却时，等待最早一个冷却时间到期。

9\.

不使用固定轮询代替冷却等待。

10\.

分组模式、成员列表或 Relay 配置变化时清理旧运行时状态。

一个成员在预算内的失败只继续该成员的重试；预算耗尽后才进入冷却。

4\. 通知

首版采用：

•

全局 Webhook 目标

•

全局失败阈值

•

通用 HTTP Webhook

•

故障和恢复都通知

默认值：

manual\_failure\_threshold = 10

failover\_channel\_threshold = 3

手动模式的连续失败次数按分组累计，成功后清零。

故障转移模式的失效渠道数等于当前处于冷却状态的成员数量。达到阈值时只通知一次，恢复到阈值以下时发送一次恢复通知。

5\. 错误可见性

采用状态流和日志提示：

•

服务端继续负责重试和切换。

•

WebUI 和 companion 展示“渠道异常，正在重试”。

•

不把提示文本插入模型输出。

•

首字节提交前可以继续重试和切换。

•

首字节提交后不得更换渠道。

•

最终耗尽重试时返回协议合法的 503 上游错误。

•

服务端不能保证任意外部客户端自动重连。

6\. 过滤功能

当前阶段只降低正则使用门槛：

•

•

增加复制按钮。

•

•

•
